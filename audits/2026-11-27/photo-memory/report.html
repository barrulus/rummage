Photo memory and scrolling tests

27 November 2026 · Local branch feat/photo-library · Production source at 09b233b.

Cold-cache preview misses were reproduced. Repeated traversals largely recovered once thumbnails were cached. The bounded runs below did not reproduce the reported 1 GiB application footprint. They do not prove the absence of leaks or retention during longer, mixed-use or SSHFS sessions.

Dataset and indexing

The read-only local source contained 18,344 files (40.4 GiB) in 75 directories. All 14,268 photo candidates completed metadata attempts; 14,256 had usable dimensions. Twelve files named .jpg lacked JPEG headers and were independently identified as generic binary data. They were marked unreadable and did not stop the scan. The origin of that malformed data is unknown.

The unchanged rescan took 66.875 seconds, with zero repeated metadata decodes. Both scans checked 18,418 entries. SQLite integrity and foreign-key checks passed; pending metadata claims were zero. The first test session was externally terminated after 500.85 seconds; an isolated companion finished the remaining metadata in 68.04 seconds before the rescan. There is no uninterrupted cold-import timing or single-process end-to-end leak measurement.

Indexing-only parent sampled RSS peaked at 15.2 MiB. The image helper briefly reached 299.4 MiB, later fell to 87.1 MiB, and retired during the rescan. The final process tree was 13.9 MiB RSS. This benchmark has no UI texture cache and does not apply the application's malloc-threshold setup.

The reported 256 MiB thumbnail budget limits estimated texture storage, not the entire process or helper pool. Texture accounting is not an additional RSS figure to sum blindly: driver/GPU mappings and shared memory have different accounting. The source code's completed textures are bounded by this cache; pending pixels, catalog rows, fonts, other views and allocator arenas are separate.

A disposable allocator self-test freed 126 MiB and then reclaimed about 126 MiB of RSS with malloc_trim while its free-chunk counter remained about 126 MiB. The actual large-three run likewise returned 18.3 MiB of RSS while its free-chunk counter fell by only about 0.2 MiB. Therefore the existing “freed but kept” label describes allocator address-space accounting, not necessarily resident RAM. Live allocations, RSS and cache ownership need to be read together.

A read-only header audit of the existing user thumbnail cache examined 76,369 PNG headers across the four size tiers. None exceeded its tier dimensions; no headers were unreadable. This rules out oversized cached-image dimensions in that sample, not every possible cache or long-session issue.

Allocation tracing and automated checks

Heaptrack on a separate 124-photo, 181.9 MiB indexing fixture completed all metadata and an unchanged rescan. Parent peak live heap was 2.86 MB; 542,853 allocation calls were recorded, about 65% attributed to SQLite. Outstanding allocations at exit were 4,512 bytes (stdout buffering and thread-local storage). This small parent-only workload does not test long-running UI leaks; profile timings include profiler overhead.

A separate UI Heaptrack run loaded all 14,268 rows and recorded 600 Down steps. Peak requested live heap was 81.94 MB; 10,122,163 allocation calls were recorded. Outstanding at trace end was 775.63 KB, primarily Fontconfig and graphics/library initialization. Those process-lifetime allocations are not automatically unreachable leaks. JSON map copies were the largest identified stack category (27.40 MB), making catalog representation an efficiency target. Merged stack-category peaks are not additive; helpers and GPU allocations are excluded from this trace.

The UI workload reached its completion marker and Heaptrack finalized its trace, but the outer collector failed during profiler-wrapper teardown and did not capture the application OS exit status. This invocation is not counted as a passing harness test. The collector was subsequently fixed to use record-only mode and handle process teardown; its separate cleanup validation is recorded in checks.json.

The existing memory tests passed (2 cases, 28 assertions), as did thumbnail and preview tests including SVG (26 cases, 443 assertions). Twelve benchmark-metric tests passed, along with the standalone allocator-probe validation. Production source and the normal application executable were not changed by this work; the rendering probes are compiled into separate temporary objects.

Limits and follow-up

  • These tests use a fresh application, local files, an isolated catalog/cache/config, default theme, scale 1, a 300-pixel inspector and a private hardware-rendered 1280×960 120 Hz display. They do not exercise the user's desktop or inject keyboard events there.
  • Navigation is dispatched through Browser::key from the test event loop. Frame callbacks measure compositor pacing, not physical input-to-photon latency. The host was not exclusively idle; some probe compilation overlapped the first four runs. Treat geometry comparisons as observations, not a controlled absolute speed ranking.
  • Only 14,268 candidates were available locally, versus 30,834 in the original report. The matrix covers preview/grid use and a bounded metadata overlap, not a long session involving every feature, existing user caches, Quick Look, or SSHFS.
  • RSS alone cannot prove a leak, and returning free pages does not prove all remaining memory is needed. Repeated live-allocation growth after equivalent settled work would require allocation-stack investigation.
  • Next focused reproduction should preserve the original session workload and source/cache conditions if the 1 GiB footprint recurs. Preview request prioritization and cache-tier reuse are candidates for separate measured improvements; no production performance fix is claimed here.
