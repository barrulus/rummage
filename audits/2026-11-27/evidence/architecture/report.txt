# Architecture, redundancy, build and packaging audit

Audited snapshot: `1dd2368783d814e86268fd2c388ee41671c66ae8`, branch `feat/photo-library`, in `/tmp/rummage-photo-library`. Comparison baseline: `63ca25bc` (full identity in `snapshot.txt`). Date: 2026-11-27. This is an audit, not a remediation patch. No source edits, commits, installs, remote operations, or shared build writes were performed.

## Results that matter

1. The frozen branch **fails the actual website link gate**, despite passing the Markdown documentation checker. The download page still advertises discontinued preview packages; the new Photo Library guide has not been added to the website navigation/content generation.
2. The new native photo UI has **avoidable work proportional to all loaded rows on each frame**, even with the information pane hidden. Opening bulk Properties adds a **quadratic selected-ID membership loop**.
3. Every successful background batch refreshes the entire loaded collection and watcher inventory. Continuous scrolling makes that work grow with browsing history, rather than with the number of rows actually changed or visible.
4. The client duplicates the backend's pending-metadata lookup and repeatedly opens/closes the catalog around each metadata item. This is a genuine redundant work path, unlike most of the small source clones found by the textual scan.
5. The packaging design is consistent with the requested boundary: standard previews, one optional photo module, no replacement launcher. I found **no additional confirmed package ownership collision** in the recipes. Actual old-to-new package upgrades were not run, so this is not a runtime upgrade certification.
6. New photo controls and status strings mostly bypass translation extraction. A successful strict i18n check does not establish localization coverage for these strings.

No new critical/data-loss finding is asserted by this architecture audit. Catalog safety, native stress timings and full-application sanitizer results are owned by the other audit tracks and must be incorporated separately. Targeted core ThreadSanitizer results from this track are recorded below.

## Findings

Severity vocabulary: **P2** = concrete correctness/integration defect or material efficiency problem to fix before broad release/use at the intended scale; **P3** = maintenance/coverage improvement. Confidence is separate from severity. Exact source line numbers below refer to the frozen snapshot.

### ARCH-01 — Website packaging instructions and Photo Library route are broken

**P2; introduced integration regression; confidence high; runtime reproduced.**

- `website/layouts/downloads.html:22` advertises matching `rummage-media`/`rummage-pdf` packages and “all four packages” in Void. It links `/docs/install/#optional-preview-packages`.
- That section was replaced by `docs/install.md:109` (“Photo Library add-on”); the previous anchor no longer exists.
- `docs/configuration.md:92` now links `photo-library.md`, but `website/data/navigation.toml:1` and its following groups do not register the new guide. The site builds docs from that explicit navigation list, so `/docs/photo-library/` is missing.
- The template/navigation files are inherited unchanged, but changing their dependent docs/package contract introduced the broken integration on this branch.

Actual `website/check.py` output:

```
downloads/index.html: missing anchor /docs/install/#optional-preview-packages
docs/configuration/index.html: missing target /docs/photo-library/
```

Recommendation: update website package copy and add the guide to navigation/content generation; rerun the generated-site checker, not only `scripts/check-docs.py`. Also remove stale “optional native rummage-pdf package” wording in `THIRD_PARTY.md:22` and optional-media/PDF source-map wording in `contributing/architecture.md:35`; these are secondary wording issues, not extra failing routes.

### ARCH-02 — Inspector snapshot construction scales with the whole collection on every frame, and quadratically for bulk Properties

**P2; introduced; confidence high for complexity/call path; no native timing measured here.**

- `src/views/src/browser.cpp:4188` unconditionally calls `photo_library_->properties(true)` while showing photos, before checking whether/how the information pane will be rendered. Hiding the pane does not avoid this work.
- `src/views/src/photo_library.cpp:214` finds the focused row through a linear scan of `rows_`.
- `src/views/src/photo_library.cpp:998` then loops through **every** loaded row and searches the `result.ids` vector with `std::ranges::find`, even for a focused-only single-ID snapshot.
- Bulk annotation opening calls the same function with the selected-ID vector. Selecting all N loaded photos entails N(N+1)/2 ID comparisons in that loop (the sum of successful search positions), plus JSON copying and field comparisons. For N=30,000 that is 450,015,000 comparisons; for 100,000 it is 5,000,050,000. These are operation-count derivations, not elapsed-time claims.
- `PhotoLibrary::selected_snapshots_` already provides an ID-indexed source for selected metadata, so the quadratic membership lookup is avoidable without redesigning the catalog.

Recommendation: direct lookup for the focused ID; use an ID set/map for bulk snapshots; cache the rendered snapshot against collection/selection revisions; skip rebuilding it while the pane is not shown. Preserve unknown/mixed values for selections outside the loaded window. Measure native Properties-open and scroll-frame times at 1k/10k/30k/100k after the fix.

### ARCH-03 — Metadata batches trigger full-prefix queries, full UI republish, and full watch inventories

**P2; introduced; confidence high for amplification; runtime cost to correlate with backend/UI stress results.**

- `src/views/src/photo_library.cpp:832` treats any `worked=true` response alike: refresh all watcher subscriptions, refresh the visible collection, then schedule more work. The client also sets `worked=true` after metadata processing (`src/photo_client/src/client.cpp:268`), so no discovery change is required.
- `PhotoLibrary::query` at `photo_library.cpp:568` preserves the already-loaded prefix length, then refetches it from offset zero in chunks of at most 1,000 (`:588`). This is necessary to preserve an existing prefix with the present implementation, but it is far more work than refreshing four changed metadata rows.
- `PhotoLibrary::publish` at `:501` rebuilds all `fs::Entry` objects and re-evaluates selection on the UI thread.
- Each backend query does COUNT plus its page query (`src/photos/src/catalog.cpp:645`, `:670`), and `photo_json` at `:574`/`:578` prepares an individual tags query and albums query for **each row**.
- At 30,000 loaded rows, one refresh therefore performs 30 page requests, 30 COUNTs, 30 page SELECTs, and 60,000 per-photo tags/albums SELECTs, before jobs and watcher requests. The cadence is limited by actual I/O/query completion; this report does not multiply that by an assumed frame rate or claim a measured queries-per-second figure.
- `SourceWatcher::refresh_subscriptions` restarts a full `watch_paths` traversal. Existing registrations also consume the 16-per-turn budget (`source_watcher.cpp:160–172`) and queue a 10 ms continuation while pending (`:201`). At 4,096 already-registered directories, traversal requires at least 256 registration batches, in addition to paged database work. If new refresh requests arrive during a traversal, `rerun_` requests another full pass.

Recommendation: distinguish discovery/location changes from metadata-only changes in work responses; refresh watch paths only when their revision changes (plus the existing availability timer); update affected metadata rows or invalidate a bounded window. Reuse prepared tag/album statements or batch enrichment for each page. Coalescing concurrent refreshes already helps; it does not remove the full-prefix work.

### ARCH-04 — Redundant metadata selection and per-item catalog initialization

**P2 efficiency; introduced; confidence high for call count; cost not isolated in this track.**

- Backend `work()` already returns `metadata_pending(db, budget)` at `src/photos/src/catalog.cpp:1503`.
- The application client ignores that candidate array and requests `metadata_pending` again with its smaller decode batch at `src/photo_client/src/client.cpp:219–220`.
- Each eligible photo then performs a separate claim request (`:228`) and metadata submission (`:264`). A normal full four-photo batch makes **10 ABI requests/database opens**: work + pending + four claims + four submissions. That excludes UI refresh/jobs/watch requests.
- `rummage_photos_request` constructs `Database` for every operation (`catalog.cpp:2608`). Construction obtains the schema flock, opens SQLite, configures WAL/FULL synchronous mode, and reads the schema version (`:126–159`); destruction closes it (`:197`). These safeguards are real, but paying all initialization costs for every tiny request is not architecturally required.
- The second pending lookup may see more recent concurrent claims, so removing it must retain claim-time validation. Do not remove claims, durability, or identity checks as a performance shortcut.

Recommendation: consume a bounded subset of the first candidate list and rely on the existing claim validation, or return only the requested metadata batch from `work`. Consider a bounded connection/session owner with prepared statements, while retaining multi-process migration serialization and worker ownership rules. Coordinate with backend latency measurements before prioritizing larger connection-lifetime changes.

### ARCH-05 — Bounded watch count does not bound UI-thread remote pathname latency

**P2 conditional responsiveness risk; new caller amplifies inherited primitive; confidence high for thread/call path, medium for practical severity; not fault-injected here.**

`SourceWatcher::fetch_page` completion calls `register_batch` on the event loop (`src/photo_client/src/source_watcher.cpp:154`). Registration calls shared `DirectoryWatcher::watch` at `:187`. That function immediately invokes `inotify_add_watch` using the pathname (`src/fs/src/directory_watcher.cpp:38`). The kernel must resolve that path, which can wait on an unavailable/slow FUSE or network filesystem. A budget of 16 registrations and a 10 ms timer only bounds work *between* syscalls, not one blocked lookup. This matters for the explicitly supported external/network-source workflow.

The directory-watch primitive is inherited and correctly shares subscriptions. The new potentially thousands-of-directories source watcher is the introduced amplification. This audit did not hang a mount or measure registration latency, and does not assert that all remote mounts block here.

Recommendation: design asynchronous/path-resolution-safe watch registration with the shared watcher rather than blindly moving its currently non-thread-safe maps to a worker; fault-inject a slow/unresponsive FUSE lookup and require input responsiveness while subscriptions are being established.

### ARCH-06 — New Photo Library strings bypass translation coverage

**P2 usability/integration; introduced; confidence high.**

`src/views/src/photo_library.cpp` has no `i18n::tr`, `trf`, or `mark` calls. New literals such as `Add folder…` (`:1167`), `Pause background work` / `Resume background work` (`:1228`), `Gentle background pace` (`:1232`) and the formatted metadata progress text (`:939`) are absent from all seven message catalogs. `Enable Photo Library` in `settings_dialog.cpp:226` likewise has no translation entry. The diff adds only five entries per language (Gallery label, Mixed values, No results, Photo Library, Add to Photo Library).

The existing generic Settings renderer may call `tr(field.label)` dynamically, but absent catalog keys still fall back to English; raw formatted status text cannot be translated by that lookup. `scripts/i18n-check.py:59` extracts explicit `tr`/`trf`/`mark` calls, so its strict pass is not evidence that these feature strings are covered.

Recommendation: mark/extract new UI messages and use formatted/plural translation helpers, then fill the catalogs. Add a non-English native feature-path check. Backend diagnostic localization needs a separate policy, not blind translation of machine-valued JSON states.

### ARCH-07 — Details rebuilds its flat/tree row index every frame

**P3 inherited efficiency hotspot; confidence high; no new branch regression claimed.**

`DetailsView::draw` calls `rebuild_rows` at `src/views/src/details_view.cpp:567`; `append_rows` at `:94` copies an owning shared pointer/index record for every entry. The baseline already does this (baseline draw call at line 563). Photo collections increase how often users may retain tens of thousands of rows while only a few dozen are visible, but the algorithm itself is inherited.

Recommendation: cache flattened rows by folder/expansion revisions. Measure before changing tree-expansion behavior. Do not label this inherited work as newly copied photo-specific rendering.

## Targeted core ThreadSanitizer validation

Executed after all serial performance measurements finished, against unchanged HEAD `1dd2368783d814e86268fd2c388ee41671c66ae8`. Direct compilation used GCC 16.2.0 with `-std=c++20 -O1 -g -fno-omit-frame-pointer -fsanitize=thread -pthread -fPIE -pie`. The instrumented production translation units are EventLoop, WorkerPool and logging; unchanged existing EventLoop/WorkerPool tests include the header-only WindowSession lifetime checks. Scratch-only test files and binaries are under `architecture/tsan/`; no shared build directory or tracked source was changed.

The deliberate data-race positive control emitted a full `WARNING: ThreadSanitizer: data race` report and expected exit 66. This confirms the selected runtime detects a race on this host; no startup mapping limitation was encountered. It is an intentional control, not a production finding. No suppression lists or ASan preload were used.

| Run | Result | Cases | Assertions | Elapsed |
|---|---|---:|---:|---:|
| Positive control | Expected race report, exit 66 | — | — | 0.032 s |
| Core, randomized seed 731 | Exit 0, no TSan diagnostics | 21 passed | 46,199 passed | 0.414 s |
| Core, randomized seed 732 | Exit 0, no TSan diagnostics | 21 passed | 46,199 passed | 0.414 s |
| Core, randomized seed 733 | Exit 0, no TSan diagnostics | 21 passed | 46,199 passed | 0.414 s |

Each core run includes all 18 existing cases plus three added stress cases: four concurrent streaming workers cancelled from another thread over 20 rounds, eight concurrent EventLoop producers delivering 4,096 callbacks exactly once over 10 rounds, and pool teardown with 64 submitted streaming jobs and later-destroyed callback owners over 20 rounds. The cancellation test waits for all workers to start and emit before cancellation; it then drains pending deliveries after pool destruction. Submission and destruction obey the loop-thread contract. Process timeouts bound the control (30 s) and each core run (120 s), with inner 20 s watchdogs for posting/cancellation tests. Core compilation succeeded in 21.854 s. Durations describe this validation run, not performance benchmarks.

Conclusion: no race report was observed in these exercised core paths. This is targeted concurrency/lifetime coverage, not proof that the entire application or uninstrumented libraries are race-free. UI, decoder, SQLite, platform, source watcher and real network filesystem concurrency are outside this harness. Detailed commands, source hashes, runtime options and exits are in `tsan/results.json`; complete output is in `tsan/control.log` and `tsan/core-{1,2,3}.log`; reproduction instructions and test source are alongside them.
