SSHFS, preview delays and retained memory

27 November 2026 · Local branch feat/photo-library · Production code unchanged during testing.

The large footprint was reproduced. Scrolling over SSHFS while repeatedly refreshing the entire loaded catalog reached about 1.5 GiB main-process RSS. At the settled checkpoint, 1,319.9 MiB was free allocator capacity and 152.5 MiB was live. Explicit reclamation reduced RSS from 1,549.6 to 238.0 MiB while live allocations stayed exactly unchanged. This reproduces allocator retention, rather than demonstrating equivalent growth in live objects.

SSHFS also caused severe preview delays in the matched-file experiment. The memory mechanism is not exclusive to SSHFS: a local-catalog scheduling control reproduced about 612 MB of free retained chunks without reading any image data or accessing SSHFS. The evidence identifies repeated full-catalog JSON rebuilding and worker-arena retention as a concrete issue in Rummage; it does not establish that network transport alone causes it.

Matched local and mounted files

Both private catalogs contained 14,268 photo candidates from the same five folders, with identical normalized relative paths, sizes, modification times (including nanoseconds), and default SQL ordering. Metadata was pending and background work paused in both. All 1,803 selected paths, including Home and 600 Down steps repeated three times, matched across the two runs. Content was not independently rehashed; the local dataset was the user's copy.

Each run used a fresh thumbnail cache and a private hardware-rendered display, with three columns, 192-pixel grid thumbnails, a 300-pixel inspector, and a nominal 25 Hz input cadence. Remote repeats were not fully warm: the SSHFS run produced only 375 large and 58 x-large cached thumbnails, versus 1,803 large and 600 x-large locally. No thumbnail errors were logged. Selection advancement and preview readiness are distinct metrics.

Live UI memory

MiB means 1,048,576 bytes. Main RSS and app/helper PSS peaks are sampled once per second; the trim checkpoint uses in-process glibc and /proc counters. PSS apportions shared pages. The shared SSHFS daemon and SSH transport were observed separately and are excluded from app/helper totals. During the matched remote run, their PSS stayed around 56 MiB and 2.7 MiB respectively; those processes did not account for the GiB-scale growth inside Rummage.

The refresh-only and refresh-plus-scroll workloads each completed 24 serialized calls through the application's public PhotoLibrary::refresh path, at least one second apart, with the full 30,834-row view loaded. Full-query refreshes can stat source roots; these UI cases are not claimed to avoid all SSHFS activity. The separate local allocator control below is what establishes that the network is unnecessary for the retention mechanism.

Controlled worker-arena experiment

The same 12 complete 14,268-photo queries were run sequentially, first on one persistent thread and then with one query on each of 12 persistent threads. Each JSON payload was destroyed before the next query. Both use the same compiled probe, local catalog, and the application's 16 MiB malloc mapping threshold. No photo decoding or SSHFS access was involved.

This isolates scheduling across arenas from query count and live-object accumulation. Forced thread rotation is a controlled upper-bound demonstration, not a direct per-thread trace of the real UI. The real UI's larger growth under simultaneous refresh and preview work is consistent with this mechanism.

After trimming, the free-chunk counter can remain large even though the pages are no longer resident. In the UI scrolling/refresh case it remained around 1,319.7 MiB after RSS fell to 238.0 MiB. The “freed but kept” counter must therefore be interpreted alongside RSS; it is not a direct measure of resident RAM.

Catalog history and refresh triggers

A read-only backup of the user's database contained 92,291 records: 30,834 current/visible records and 61,457 historical records marked replaced. These are catalog records. In a deliberately stratified 48-record sample, device, size and modification times matched current files, but inode mismatches occurred in 6/12 online, 12/12 changed, and 12/12 historical replaced records; the 12 unreadable records matched. This is not a random estimate of the whole catalog.

Current per-read inode instability was not observed: all 14,268 common files had identical inodes in two fresh SSHFS scans, and a small repeat-stat sample stayed unchanged after 143 seconds. The historical inode changes are real; their origin, including whether a remount or remote replacement occurred, is not established by this test.

The production path is specific: catalog.cpp:index_file marks an existing row replaced when device/inode differs before comparing size and modification time. Discovery changes lead to PhotoLibrary::refresh(). PhotoLibrary::query(false) rebuilds the entire loaded prefix as JSON in worker tasks, collecting pages of up to 1,000 rows. Date-based metadata sorting/filtering can also trigger full refreshes. This gives source changes a route to repeated large temporary allocations.

The native-rescan case uses a separate copy of the existing catalog. A plain native refresh returned its already-running metadata job without restarting discovery. Native job retry was therefore used on the test copy to queue root discovery, and that copy was unpaused. That native rescan reached 803.5 MiB main RSS without a forced UI-refresh loop. At the final input-idle checkpoint, RSS was 803.0 MiB, live allocations 198.2 MiB and free allocator chunks 527.1 MiB. Trimming reduced RSS to 287.6 MiB while concurrent work increased live allocations to 201.4 MiB; three seconds later RSS was already 408.8 MiB. Reclamation alone therefore does not prevent regrowth while the allocation pattern continues. The rescan checked 2,560 additional entries and added 1,198 replaced historical rows, while visible photos stayed at 30,834. Background discovery remained active at exit; an input-idle interval must not be mistaken for completed background work.

The 24-refresh scrolling stress reclaimed 1,311.6 MiB RSS with live allocations exactly unchanged. Its texture accounting remained at the existing budget with zero pending pixel bytes, so clearing the image cache was not needed for that reduction.

What this establishes

  • SSHFS materially delayed previews in this matched workload, including repeated passes whose thumbnail cache remained incomplete.
  • Large catalog refreshes can leave substantial freed allocator memory resident. The local scheduling control and real UI reclamation measurements explain how this can happen without a matching live-allocation leak.
  • The original session's exact sequence is not known. Current healthy-connection tests do not prove which past mount or file operation created historical inode differences, and do not rule out other leaks.
  • Production fixes should target avoiding full-prefix reconstruction for routine discovery updates, limiting how large catalog allocations spread across workers, and controlled reclamation when work settles. Selected-preview prioritization and bounded/cancel-aware file work deserve separate performance testing.

Scope and evidence

The shared mount was neither remounted nor disconnected; source photos were only read. Original catalog, user application state, and normal executable were not modified. Test catalogs, caches, configuration, and private displays were isolated. OS/server/SSHFS caches were not cleared, the host was not exclusively idle, and these single sequential runs are not a statistically controlled benchmark of all SSHFS configurations.

Raw traces stay in /tmp and can contain filenames. Committed evidence contains accounting and aggregate results, not photo pixels or the user's database. All five UI runs completed with exit status zero. Thirteen metric tests and C++/Python formatting checks passed. All private test applications and compositors exited; the shared mount daemon and SSH transport remained alive. Detailed reproduction commands and raw locations are in REPRODUCE.txt.
